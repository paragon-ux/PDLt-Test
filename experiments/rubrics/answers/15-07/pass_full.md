1. **Saturation:** throughput grows nearly linearly to 200 users (2,560 req/s) and then plateaus (2,680 at 300, 2,710 at 500, 2,650 at 1,000), while avg latency doubles from 200 to 300 users and p99 jumps 210 → 890 ms. Saturation is between 200 and 300 users.
2. **Bottleneck:** CPU. It is 91% at 200 users and 98-99% beyond, exactly where throughput stops growing. DB connections also hit a ceiling of 150 at 200 users (a pool limit), so requests queue for connections too, but CPU is pinned regardless. Memory (40-78%) is not limiting.
3. **Drop at 1,000 users:** with CPU saturated, more concurrency adds context switching and queueing; requests time out (23.4% errors), and timeouts, retries and error handling consume CPU without completing work, so goodput falls below the plateau. Memory pressure (78%) adds GC overhead.
4. **Maximum recommended:** ~200 concurrent users (p99 210 ms, 0.1% errors). Running at 150-180 leaves headroom for spikes.
5. **Scaling:** add application instances behind the load balancer (the CPU bottleneck scales horizontally); profile hot paths and cache responses to cut CPU per request; resize the DB pool per instance against database capacity; add load shedding (429s) or admission control at ~200 concurrent users per instance so overload degrades gracefully.
