**Sharding Strategy Design**

### 1. Users Table (`users(id, username, region, created_at)`) – ~100M rows
- **Chosen shard key:** `region`
- **Justification:**
  - Queries:
    - *Region‑based lookup*: Directly filtered by `region`, making the query single‑shard.
    - *User timeline*: Timeline queries need the user's own data (profile, follower list) which is accessed via `id`/`username`. These are read‑only lookups that can be routed to the shard containing the user’s `region`. Since the timeline query pulls posts from the `posts` table (sharded by `author_id`), it remains a cross‑shard join, but the user‑side data stays local.
  - Load‑balancing: Assuming a reasonably even geographic distribution, `region` spreads users across shards. Hotspots are mitigated by sub‑sharding (e.g., `region` + hash(`id`)) if a region becomes dominant.

### 2. Posts Table (`posts(id, author_id, content, created_at)`) – ~5B rows
- **Chosen shard key:** `author_id`
- **Justification:**
  - Queries:
    - *User timeline*: Retrieves posts where `author_id` is in the follower list. Partitioning by `author_id` means each author’s posts live on a single shard, so fetching a timeline becomes a scatter‑gather across the few authors a user follows – still efficient because each shard returns a small, recent slice.
    - *Full‑text search*: Full‑text indexes are often built per‑shard; distributing by `author_id` balances the index size. Search can be executed in parallel across shards, then merged.
  - Load‑balancing: Popular authors may create hotspots; mitigate with a composite key `author_id` + hash(`id`) or by splitting very high‑traffic authors into sub‑shards.

### 3. Likes Table (`likes(id, post_id, user_id, created_at)`) – ~50B rows
- **Chosen shard key:** `post_id`
- **Justification:**
  - Queries:
    - *Fetch likes for a given post*: Directly filtered by `post_id`, thus becomes a single‑shard query.
    - *Count likes per post*: Same as above; aggregation runs locally on the shard holding the post’s likes.
  - Load‑balancing: Popular posts can cause hotspot shards. To alleviate, shard by `post_id` + hash(`user_id`) or use a two‑level sharding where extremely hot posts are further split.

### 4. Follows Table (`follows(follower_id, following_id, created_at)`) – ~2B rows
- **Chosen shard key:** `follower_id`
- **Justification:**
  - Queries:
    - *Retrieve a follower’s list*: Filtered by `follower_id`, thus single‑shard.
    - *Count followers for a user*: Requires scanning rows where `following_id = <target>`. This becomes a scatter‑gather across shards, but the count can be pre‑aggregated (materialized view) or cached to reduce cross‑shard cost.
  - Load‑balancing: Distributes follow relationships evenly assuming a roughly uniform follower distribution. Hot accounts with massive follower counts may benefit from secondary indexing on `following_id`.

### 5. Query locality analysis
| Table | Query | Shard Key | Local (single‑shard) | Scatter‑Gather |
|-------|-------|-----------|----------------------|----------------|
| Users | Region lookup | `region` | ✅ (region filter) | ❌ (timeline uses posts) |
| Users | Profile fetch by `id` | `region` | ✅ (if `id` maps to same region) | ❌ (if routed solely by `id`) |
| Posts | Timeline (by author) | `author_id` | ❌ (multiple authors) | ✅ (parallel per‑author) |
| Posts | Full‑text search | `author_id` | ❌ (search across shards) | ✅ (parallel) |

### 6. Trade‑off discussion
- **Load balancing vs. hotspot risk:**
  - Choosing geographic `region` for users spreads load but can create hotspots if a region dominates traffic. Adding a hash component mitigates this.
  - Sharding posts by `author_id` aligns with write patterns (authors create posts) but makes timeline reads scatter‑gather across many shards. Popular authors may overload their shard; composite keys or dynamic re‑sharding can help.
  - Likes sharded by `post_id` gives perfect locality for per‑post operations but can suffer from viral posts. Sub‑sharding by `user_id` distributes the load.
  - Follows sharded by `follower_id` ensures fast retrieval of a user’s follow list, but follower‑count queries become cross‑shard. Caching counts or maintaining a secondary count table reduces this cost.
- **Cross‑shard joins:**
  - Most user‑centric reads (timeline) already require joining users → follows → posts; with the proposed keys, the join will involve fetching follower lists (single‑shard) and then pulling recent posts from multiple post shards. This is acceptable because the join is read‑only and can be parallelized.
  - Full‑text search inherently needs to query many shards; distributed search engines handle this efficiently.
- **Scalability:**
  - The keys selected map naturally to write patterns (user creation, post creation, like insertion, follow insertion) keeping inserts localized to a single shard.
  - Reads that become scatter‑gather are still scalable due to parallelism; the main concern is latency for timeline assembly, which can be mitigated with caching layers or pre‑computed feed tables.

**Recommended Shard Keys**
- `users`: `region` (with optional hash of `id` for hot regions)
- `posts`: `author_id`
- `likes`: `post_id`
- `follows`: `follower_id`

These choices balance write locality, query performance, and load distribution while keeping hotspot risk manageable through secondary hashing or auxiliary indexes where needed.
