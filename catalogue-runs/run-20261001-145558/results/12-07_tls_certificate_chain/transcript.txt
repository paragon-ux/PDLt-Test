ASSISTANT> **Explanation of the error**

The message `unable to get local issuer certificate` means OpenSSL could not find a trusted issuer (intermediate or root CA) for the leaf certificate presented by the server. In the displayed `s_client` output only the leaf certificate (CN = api.example.com) is shown in the "Certificate chain" section – the intermediate CA certificate that issued the leaf is missing. Because the intermediate is not provided, the client cannot build a complete chain up to a trusted root, resulting in the verification failure.

**Why the chain contains only one certificate**

* The server is configured to send only its leaf certificate.
* The intermediate CA certificate ("Example Intermediate CA") is not concatenated to the leaf certificate in the server’s TLS configuration, so OpenSSL never receives it.

**Role of the intermediate CA certificate**

* The intermediate CA bridges the trust between the leaf certificate and a root CA that is already trusted by clients (e.g., in the OS or browser store).
* Clients normally do not have the intermediate certificate locally, so the server must supply it during the TLS handshake.
* The intermediate certificate can be obtained from the CA that issued the leaf certificate – often via a downloadable file from the CA’s website or by extracting it from the CA’s bundle.

**Server‑side fix – steps**

1. **Obtain the intermediate certificate**
   ```bash
   # Example: download from the CA’s site (replace URL with the actual one for your CA)
   curl -o intermediate.pem https://example-ca.com/intermediate.crt
   ```
   Alternatively, retrieve it from the CA’s bundle:
   ```bash
   openssl x509 -inform PEM -in intermediate_bundle.pem -out intermediate.pem
   ```
2. **Create a full chain file**
   The order must be leaf → intermediate → (optional) root. Assuming you already have `leaf.pem` (the server certificate) and `intermediate.pem`:
   ```bash
   cat leaf.pem intermediate.pem > fullchain.pem
   # If you also want to include the root (not required for most servers):
   cat leaf.pem intermediate.pem root.pem > fullchain.pem
   ```
3. **Configure the server to use the full chain**
   *For Nginx:*
   ```nginx
   server {
       listen 443 ssl;
       server_name api.example.com;

       ssl_certificate /etc/ssl/certs/fullchain.pem;   # ← full chain file
       ssl_certificate_key /etc/ssl/private/api.key; # ← private key
   }
   ```
   *For Apache (mod_ssl):*
   ```apache
   SSLEngine on
   SSLCertificateFile    /etc/ssl/certs/leaf.pem
   SSLCertificateChainFile /etc/ssl/certs/intermediate.pem   # older Apache versions
   # Newer Apache can use a combined file:
   SSLCertificateFile /etc/ssl/certs/fullchain.pem
   SSLCertificateKeyFile /etc/ssl/private/api.key
   ```
   *For other servers (e.g., Java/Kestrel, HAProxy), consult the vendor documentation – the principle is the same: provide a file that contains the leaf followed by any required intermediates.
4. **Reload/restart the server**
   ```bash
   # Nginx
   sudo nginx -s reload
   # Apache
   sudo systemctl reload apache2
   ```

**Verification after the fix**

*Check the chain with `s_client`*:
```bash
openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts
```
You should now see both the leaf and the intermediate certificate listed under "Certificate chain" and the verification line should read `Verify return code: 0 (ok)`.

*Verify the chain with `openssl verify`* (using the same files you supplied to the server):
```bash
# Assuming you have a copy of the full chain and a trust store containing the root CA
cat fullchain.pem > chain.pem
openssl verify -CAfile /path/to/root-ca.pem chain.pem
```
The output should be:
```
chain.pem: OK
```

**Client‑side debugging steps**

1. **Use `-servername` (SNI) when testing** – some servers host multiple certificates on the same IP.
2. **Display the full chain**:
   ```bash
   openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts
   ```
   Verify that the intermediate certificate appears after the leaf.
3. **Force a specific trusted store** (useful if the client’s store is missing the root):
   ```bash
   openssl s_client -connect api.example.com:443 -servername api.example.com \
       -CAfile /path/to/truststore.pem
   ```
4. **Inspect the verification return code** – a non‑zero code indicates a problem; `0` means the chain is trusted.
5. **Use `openssl verify` on the downloaded certificates** as shown above to isolate whether the problem is on the server side (missing intermediate) or on the client side (untrusted root).

By supplying the missing intermediate certificate in the server’s TLS configuration and verifying with the commands above, the `unable to get local issuer certificate` error will be resolved.
