**Analysis**
The original program declares two global locks, `lock_a` and `lock_b`. The function `transfer_ab` acquires `lock_a` **then** `lock_b`, while `transfer_ba` acquires `lock_b` **then** `lock_a`. When two threads invoke these functions concurrently, each may hold one lock while waiting for the other, creating a classic *lock ordering violation* that can lead to a deadlock. Because the acquisition order is inconsistent, a situation where Thread‑1 holds `lock_a` and waits for `lock_b` while Thread‑2 holds `lock_b` and waits for `lock_a` can occur, causing both threads to block indefinitely. This deadlock is intermittent because it depends on the scheduling of the threads.

**Corrected Version**
The fix is to enforce a consistent lock acquisition order. The simplest approach is to always acquire `lock_a` before `lock_b`. Both transfer functions are rewritten to respect this order. Alternatively, a single lock could be used, but the example keeps two locks to demonstrate ordering.

import time

# Global synchronization primitives
lock_a = threading.Lock()
lock_b = threading.Lock()
results = []

# Helper to acquire locks in a consistent order (a then b)
def acquire_locks_in_order():
    # Always lock A first, then B
    lock_a.acquire()
    lock_b.acquire()

def release_locks_in_order():
    lock_b.release()
    lock_a.release()

def transfer_ab(amount):
    # Consistent lock ordering: a then b
    acquire_locks_in_order()
    try:
        results.append(('ab', amount))
    finally:
        release_locks_in_order()

def transfer_ba(amount):
    # Consistent lock ordering: a then b (same as above)
    acquire_locks_in_order()
    try:
        results.append(('ba', amount))
